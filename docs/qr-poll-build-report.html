1QR Poll이란?

강의장에서 쓰는 "가벼운 Slido" — 청중 참여를 실시간으로 모으는 도구

발표자가 화면에 QR코드를 띄우면, 청중은 폰으로 찍어 익명으로 메시지·질문·투표를 남긴다. 결과는 발표자 화면에 실시간으로 집계된다. 유료 서비스 Slido의 핵심만 떼어 직접 만든 버전이다.

🙋 청중 /r/코드

폰으로 QR 스캔 → 익명 메시지·👍리액션·객관식 투표. 발표자가 지금 띄운 것만 보인다.

🖥️ 빔프로젝터 /present/코드

큰 화면 전용(읽기 전용). QR + 실시간 결과. 발표자가 고른 질문이 실시간 전환된다.

🎤 관리자 /admin/코드

강사 조종석. 질문 띄우기/다음, 메시지 삭제·고정, 결과 내보내기(txt). 비밀키로 보호.

💬 챗룸(백채널)

질문·투표와 별개로 항상 열리는 캐주얼 채팅. 오른쪽 위 플로팅 버튼으로 연다.

💡 개념 하나 — "실시간"은 어떻게 되나요? (SSE)

SSE(Server-Sent Events)는 쉽게 말해 "서버가 브라우저 쪽으로 새 소식을 계속 밀어주는 한 방향 통로"다. 누군가 글을 남기면 서버가 접속 중인 모든 화면에 즉시 밀어 넣어, 새로고침 없이 갱신된다.

메시지·투표"] -->|"① 전송(POST)"| S["서버
(Node)"]
  S -.->|"② 파일에 기록"| J[("JSONL 파일")]
  S ==>|"③ 실시간 push (SSE)"| P["🖥️ 빔프로젝터"]
  S ==>|"③ 실시간 push (SSE)"| M["🎤 관리자"]
  S ==>|"③ 실시간 push (SSE)"| B["🙋 다른 청중들"]

저장도 거창한 DB 없이 텍스트 파일에 한 줄씩 쌓는(JSONL) 가장 단순한 방식을 썼다.

📸 실제 화면 (실제 강의 · ewha)

실제로 진행된 강의 이벤트(ewha)의 라이브 화면. 설문 결과는 그대로, 채팅 내용은 개인정보 보호를 위해 블러 처리했다.

💡 개념 하나 — "클라우드 배포"란?

만든 걸 노트북에서만 돌리면 나만 쓴다. 배포(deploy)는 그걸 인터넷에 올려 누구나 접속하게 만드는 일이다. 이 서비스가 실제로 굴러가는 구조(ssh prod로 확인한 현재 상태):

flowchart LR
  U["🌐 사용자 브라우저
qr-poll.physical-spark.com"] --> CF["Cloudflare
Tunnel
(안전한 통로)"]
  CF --> N["OCI 무료 서버
Ampere A1 · Node
systemd로 상시 가동"]
  N --> J[("JSONL 파일
메시지·투표 저장")]
  • 서버: Oracle Cloud(OCI) Always Free — Ampere A1. 오라클이 무료로 주는 ARM 서버(Ubuntu · 4 vCPU · 24GB), 19주 넘게 무중단, 월 $0.
  • 항상 켜두기: systemd로 등록해 꺼지면 자동 재시작.
  • 연결 통로: Cloudflare Tunnel — 방화벽·포트를 열지 않고 서버를 인터넷에 안전하게 잇는다.
  • 주소: 직접 산 도메인을 통로에 연결. QR은 접속 주소를 자동으로 담는다.

이 한 문단에 설계 요소 8가지가 다 있다

① 레퍼런스로 목표"slido 같은" — 목표를 한 단어로 합의.
② 제약 먼저"가장 간단하게 / 기능은 작을 것 / todolist 수준" — 범위를 좁혀 완성률을 높인다.
③ 단계적 사고"mvp로는 … phase를 발전시켜나가며" — MVP→성장 경로 제시.
④ 선택지+판단 위임"vercel … 아니면 ssh prod … 도 되고" — 옵션을 주되 결정은 AI에게.
⑤ 운영까지 시야도메인·서버·cloudflare 언급 — "실제로 굴러가게"가 목표.
⑥ 설정 분리"설문 문구 … json/md로" — 값을 코드에 박지 말고 바꾸기 쉬운 파일로.
⑦ 검증 지시"크롬 cdp로 확인해봐 / 실제 데이터도 예시로" — AI가 실물을 보고 만들게.
⑧ 프로세스 지정"public repo … commit push … roadmap까지" — 작업 방식·산출물 기준을 못 박음.

6대가들의 프레임워크로 보면

AI 코딩을 오래 관찰해온 실무자들의 공개된 주장과, 이 프로젝트에서 실제로 벌어진 일의 대응

아래 인용은 각 인물이 공개적으로 밝혀온 관점의 요약·의역이며, 원문 그대로의 인용문이 아니다.

Andrej Karpathy · 전 Tesla AI 총괄, "vibe coding" 이라는 말을 만든 사람

① 자율성 슬라이더(autonomy slider) — AI를 얼마나 풀어줄지는 조절하는 것

AI에게 한 번에 큰 덩어리를 맡길수록 결과 검증이 어려워진다. 그는 AI를 짧은 목줄에 두고 작은 단위로 일을 시키라고 권한다. 자율성은 켜고 끄는 스위치가 아니라 상황에 맞게 밀고 당기는 슬라이더다.

이 프로젝트에서: 같은 사람이 Claude에겐 18번의 큰 지시로 맡겼고, 결과가 자주 어긋난 Codex에겐 54번의 잘게 쪼갠 지시를 보냈다. 모델을 바꾼 게 아니라 슬라이더를 내린 것이다.
Andrej Karpathy

② 진짜 병목은 생성이 아니라 검증(verification) 루프다

AI는 코드를 몇 초 만에 쏟아낸다. 느린 쪽은 사람이 그게 맞는지 확인하는 속도다. 그래서 그는 검증을 빠르게 만드는 것(눈으로 즉시 확인 가능한 화면·구체적인 작은 변경)을 강조한다.

  G["AI가 만든다
(몇 초)"] --> V{"사람이 확인한다
← 진짜 병목"}
  V -->|"괜찮다"| N["다음 단계로"]
  V -->|"아니다"| C["구체적으로 교정"]
  C --> G
이 프로젝트에서: Claude는 브라우저로 화면을 54번 직접 캡처해 확인했고, 사용자는 show the screenshot·어떻게 증명할래로 증거를 요구했다. 반대로 시각 검증이 없던 Codex 구간에서 UI 회귀가 가장 많이 생겼다.
Simon Willison · Django 공동창시자, LLM 실무 활용 기록으로 유명

③ 절대 위임할 수 없는 한 가지 — "코드가 실제로 돌아가는지 확인하는 일"

그는 LLM 코딩에서 맥락(context)을 충분히 주는 것과 정확히 무엇을 원하는지 지시하는 것이 결과를 좌우한다고 말한다. 그리고 결과를 직접 테스트하는 책임만은 사람이 진다고 못 박는다.

이 프로젝트에서: 사용자는 매번 라이브 URL에 직접 들어가 "present 하니깐 안되네?", "청중 쪽이 짤림", "투표 취소가 안 되네?" 처럼 본인이 실물을 확인했다. 실제로 Cloudflare 캐시 버그는 이 확인이 아니었으면 못 잡았다.
Addy Osmani · Google 엔지니어링 리더

④ "70% 문제" — AI는 70%까지 데려다주고, 나머지 30%에서 실력이 갈린다

AI로 초안은 놀랍도록 빨리 나오지만, 마지막 30%(엣지 케이스·일관성·정리·운영)에서 경험이 필요하다. 비개발자는 여기서 "고칠수록 새 버그가 나는" 벽을 만난다고 그는 지적한다.

이 프로젝트에서: Codex가 기능을 넓게 확장한 뒤 남은 죽은 코드·에셋 버전 불일치·사라진 데모 이벤트가 정확히 그 30%였다. 해결책은 사람이 코드를 파는 게 아니라 다른 모델에게 감사를 시키는 것이었다(프롬프트 ⑪).
Anthropic · Claude Code 실무 가이드

⑤ 탐색 → 계획 → 구현 → 커밋, 그리고 "일찍 자주 교정하라"

공식 가이드는 바로 코드부터 쓰게 하지 말고 먼저 조사하고 계획을 세우게 한 뒤 구현시키라고 권한다. 또 지시는 구체적으로, 방향이 틀어지면 끝까지 가기 전에 즉시 교정하라고 한다.

이 프로젝트에서: 첫 턴은 계획 모드로 설계 합의 후 구현했고, Codex에서도 plan을 다시 너와 만들어보자 → Implement the plan. 순서를 밟았다. 어긋나면 다시 롤백해서 … 왼쪽에 만들어처럼 즉시 되돌렸다.

업계 공통 관찰 · "명세(spec)가 곧 결과물"

⑥ 코드보다 오래 남는 건 "무엇을 왜 만드는가"라는 글

코드 작성 비용이 급격히 떨어지면서, 가치는 의도를 정확히 글로 옮기는 능력으로 옮겨간다. 잘 쓴 명세는 사람과 AI 모두를 정렬시키는 단 하나의 원본이 된다.

이 프로젝트에서: 첫 프롬프트 한 문단이 사실상 제품 명세서였다(목표·제약·배포·검증·프로세스). 이후 모든 작업이 그 문단 위에서 굴러갔고, 로드맵 문서(docs/ROADMAP.md)가 두 AI 사이의 공통 기준 역할을 했다.
여섯 사람의 이야기를 한 줄로 합치면: AI에게 무엇을·왜·어디까지를 글로 정확히 주고(명세), 한 번에 맡기는 크기를 조절하며(자율성 슬라이더), 매번 눈으로 확인하고(검증 루프), 마지막 30%는 검수로 메운다(교차 리뷰). 이 프로젝트는 우연히 그 네 가지를 다 했다.

7따라 하기 — 좋은 프롬프트 6단계

위 사례에서 뽑은, 누구나 쓸 수 있는 틀

  • 1. 목표를 레퍼런스로 — "○○ 같은 걸 만들고 싶어"
  • 2. 범위를 좁혀라 — "가장 간단하게, 딱 이 정도만" (안 만들 것도 말하기)
  • 3. 단계로 나눠라 — "먼저 MVP는 △△, 그다음 phase로"
  • 4. 선택지+판단을 맡겨라 — "A로 할까 B로 할까? 추천해줘"
  • 5. 검증을 시켜라 — "직접 실행/화면 보고 확인, 예시 데이터도"
  • 6. 모델에 맞춰 입자 조절 — 강한 모델엔 위임, 약한 모델엔 잘게 쪼개고 자주 확인
핵심은 완벽한 명세서가 아니라 "방향 + 제약 + 위임". 개발 용어를 다 몰라도 무엇을·왜·어디까지만 분명히 말하면 AI가 나머지를 채운다.

1

🎯 말한다

사람

"이런 걸 만들고 싶어" — 목표를 아는 서비스에 빗대고, 범위를 좁혀서 한 문단으로. 완벽할 필요 없다.

2

🛠️ 만든다

AI

AI가 파일을 만들고 코드를 쓰고, 필요한 도구(서버·라이브러리)를 스스로 고른다. 내 노트북에서 일단 돌아가게 한다.

3

👀 확인한다

AI가 보여주고 · 사람이 본다

말로 "됐어요"가 아니라 실제 화면·스크린샷·실행 결과로 확인. 이 프로젝트에선 AI가 브라우저로 직접 찍어 54번 확인했다.

4

🔁 고친다

사람

"이건 오른쪽 위로 / 이 글자 작게 / 이건 빼줘"처럼 구체적으로. 고민되면 "잘 모르겠는데 어떻게 할까?"라고 물어도 된다.

5

🚀 올린다

AI

인터넷에 배포해 남들이 쓰게 만든다(서버·도메인·항상 켜두기). 무료 클라우드로 $0에도 가능하다.

6

🌱 키운다

반복

한 번에 완성하지 말고 작은 버전(MVP)부터. 되면 다음 기능(phase)으로. 막히면? 더 잘게 쪼개서 부탁하면 된다.

역할 나누기 한 줄 요약: 사람은 방향·판단·검증을, AI는 실행·반복·기록을 맡는다. 코드를 몰라도 무엇을·왜·어디까지를 계속 말해주면, 서비스가 실제로 세상에 나온다.
